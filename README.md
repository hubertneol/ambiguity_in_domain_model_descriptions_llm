# Domain Model Evaluation — Controlled Experiment

Thesis experiment investigating how controlled modifications of natural-language
domain descriptions influence the UML domain models generated by ChatGPT.

Each generated model is compared against a human-authored reference model using
**Metrik-4**, which reports three scores: `class_score`, `attribute_score` and
`association_score`.

## Experimental design (fixed)

**45 cases × 5 versions × 1 ChatGPT generation = 225 generated UML models**

| Version | Condition |
|---------|-----------|
| `V0` | baseline / original description |
| `V1` | implicit information |
| `V2` | non-syntactic ambiguity |
| `V3` | semantic anomaly |
| `V4` | paraphrase relation |

Case ids are the benchmark's own folder names (`AirTravel`, `AlphaInsurance`,
… `eHome2020`), not generic indices, so every result stays traceable to the
source corpus. All design constants live in `config/experiment_config.py`.

## Experimental isolation

The directory layout enforces a separation between the text shown to the model
and the ground truth used to score it:

| Directory | Contents | Who reads it |
|-----------|----------|--------------|
| `data/` | natural-language descriptions only (`V0.txt` … `V4.txt`) | variant writing, UML generation, evaluation |
| `reference_models/` | ground-truth UML (`reference_model.puml`) | **evaluation only** |
| `generated/` | LLM-generated UML | UML generation, evaluation |
| `prompts/` | fixed executable prompts | variant writing, UML generation |
| `patterns/` | documented prompt patterns | humans |
| `results/` | evaluation outputs | export |

Reference models are stored **outside `data/`** so the agent that writes V1–V4
and the agent that generates UML never have the ground truth in scope. Were the
reference model to sit next to the descriptions, its class names, attributes and
associations could leak into the generation process — the generated model would
then partly reflect the answer key rather than the description alone, and the
measured effect of each text condition would be confounded.

Concretely:

- the **text-variant stage** needs only `data/` and `prompts/`;
- the **UML-generation stage** needs only `data/`, `prompts/model_generation_prompt.txt` and `generated/`;
- `reference_models/` becomes relevant only at **evaluation** time.

`scripts/validate_dataset.py` enforces this: any `.puml` file found under
`data/` is reported as an error.

## Project structure

```
domain_model_eval/
├── data/                       # natural-language inputs only
│   └── <case_id>/V0.txt … V4.txt
├── reference_models/           # ground truth — evaluation only
│   └── <case_id>/reference_model.puml
├── generated/                  # LLM outputs
│   └── <case_id>/<version>/generated_model.puml
├── prompts/                    # fixed prompts
├── patterns/                   # documented prompt patterns
├── scripts/                    # deterministic tooling
├── results/                    # results.csv, results.xlsx, records.jsonl
├── config/experiment_config.py # all constants and path helpers
├── requirements.txt
└── .venv/
```

## Setup

Metrik-4 is provided by `domain_model_metrics`, which is not on PyPI. Install it
as an editable package from a local checkout of *domainModel-Metrics-Comparison*,
then fetch the NLTK corpora it needs:

```bash
.venv/bin/pip install -e /path/to/VasiliySeibert-domainModel-Metrics-Comparison-<rev>
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m nltk.downloader wordnet omw-1.4 stopwords \
    averaged_perceptron_tagger averaged_perceptron_tagger_eng punkt punkt_tab
```

## Workflow

### 1. Prepare the dataset

Normalises the read-only benchmark corpus into this project. Descriptions go to
`data/`, reference models to `reference_models/`. The source corpus is never
modified, and re-running is safe.

```bash
.venv/bin/python scripts/prepare_dataset.py --source /path/to/benchmark/models --dry-run
.venv/bin/python scripts/prepare_dataset.py --source /path/to/benchmark/models
```

The source location may also be supplied via `BENCHMARK_SOURCE_DIR`.

### 2. Write the V1–V4 descriptions

Apply the prompt in `prompts/v<n>_*.txt` to each `data/<case_id>/V0.txt` and
write the result to `data/<case_id>/V<n>.txt`. `V0.txt` is never modified.

This stage must use **only** `data/` and `prompts/`.

```bash
.venv/bin/python scripts/validate_variants.py            # progress check
.venv/bin/python scripts/validate_variants.py --strict   # once all 180 are written
```

### 3. Generate the UML models

`scripts/generate_models.py` sends each of the 225 descriptions to the OpenAI
API and writes the returned PlantUML to
`generated/<case_id>/<version>/generated_model.puml`.

This stage uses **only** `data/`, `prompts/model_generation_prompt.txt` and
`generated/`.

**Experimental isolation.** Every generation is a separate, independent API
request. The message list is rebuilt from scratch for each call and contains
exactly two items: the verbatim fixed prompt, and the one description being
processed. No prior response, no other version of the same case, no other case,
no reference model and no metric score is ever included. There is no persistent
conversation and no accumulated history.

Exactly one generation attempt represents each observation — the script never
samples multiple candidates and never asks the model to revise its output.
Retries fire only on transient transport failures (timeout, 429, 5xx) and
re-send the byte-identical request.

**Install and configure:**

```bash
.venv/bin/pip install openai          # or: .venv/bin/pip install -r requirements.txt
export OPENAI_API_KEY='sk-...'        # never hard-coded; read from the environment
```

`prompts/model_generation_prompt.txt` is authoritative and is never modified by
the script. Its SHA-256 is recorded with every request.

Generation settings — model, temperature, token cap, retry policy — are
centralised in `config/experiment_config.py` under "OpenAI generation settings"
and are identical for all 225 requests.

> Check `OPENAI_MODEL` in `config/experiment_config.py` before the full run. It
> defaults to `gpt-4o`; set it to the exact model you intend to cite, and keep
> it fixed for the whole experiment.

**Run it:**

```bash
# 1. inspect the plan — no API calls, no key required
.venv/bin/python scripts/generate_models.py --dry-run

# 2. single-description smoke test
.venv/bin/python scripts/generate_models.py --case AirTravel --version V0 --limit 1

# 3. the full experiment (225 models)
.venv/bin/python scripts/generate_models.py

# 4. confirm technical completeness and formatting
.venv/bin/python scripts/generate_models.py --validate-only
```

Existing `.puml` files are **skipped by default** so a rerun cannot silently
destroy an observation. Replacing them requires `--overwrite`, which warns
before proceeding.

The `--validate-only` check is purely technical — 225 descriptions present,
every case complete, every output mapped to a description, no duplicate
case/version, every file starting with `@startuml` and ending with `@enduml`.
It never compares against the reference models.

Every request attempt appends a row to `results/generation_log.csv`: timestamp,
case, version, description path, output path, API model, temperature, token cap,
prompt and description hashes, status, attempt count, format check, token usage,
and any error.

### 4. Validate the structure

Warnings are expected while variants and models are still being filled in;
`--strict` turns them into failures once the dataset should be complete.

```bash
.venv/bin/python scripts/validate_dataset.py
```

### 5. Evaluate with Metrik-4

Iterates over all 225 generated models automatically, mapping

```
generated model (case, version)  ->  reference model (case)
```

It compares `reference_models/<case_id>/reference_model.puml` against each
`generated/<case_id>/<version>/generated_model.puml` and writes one record per
comparison to `results/records.jsonl`. Pairs whose generated model is missing
are skipped, so the script can be run while generation is still in progress.
Metric failures are recorded with an `error` field and null scores — never with
a substituted value.

When `results/generation_log.csv` exists, each result row records the API model
and temperature that actually produced that specific model, rather than the
current config defaults. Metrik-4's implementation and arithmetic are untouched.

```bash
.venv/bin/python scripts/evaluate_models.py --dry-run
.venv/bin/python scripts/evaluate_models.py
```

### 6. Export the results

Writes the long-form table (one row per evaluated model) to `results/results.csv`
and `results/results.xlsx`. With no records yet, both are written with headers
only.

```bash
.venv/bin/python scripts/export_results.py
```

Result schema: `case_id`, `version`, `provider`, `model_name`, `run`,
`input_description`, `reference_plantuml`, `generated_plantuml`, `prompt`,
`timestamp`, `temperature`, `class_score`, `attribute_score`,
`association_score`.

`provider` is fixed to `ChatGPT` and `run` to `1` for the current experiment;
both fields are carried through so a multi-provider or multi-run design can
extend the schema without changing it.
